# fips_file_crypt

Minimal worked example of using the OpenSSL 3.x FIPS provider from C++20
to do AES-256-GCM "encryption at rest" of a file, per
https://docs.openssl.org/master/man7/fips_module/.

## Layout

- `src/main.cpp` — the program: loads the FIPS provider, fetches
  AES-256-GCM with the `fips=yes` property query, encrypts/decrypts a
  file with a random key.
- `CMakeLists.txt` — finds system OpenSSL 3.x, builds `fips_file_crypt`.
- `scripts/setup_fips_module.sh` — builds the FIPS provider module
  (`providers/fips.so`) from OpenSSL source and runs `openssl fipsinstall`
  against it (this executes the FIPS self-tests). Writes its output to
  `fips-module/` and generates `openssl-fips.cnf`.
- `fips-module/` — the built module (`fips.so`) and the config
  (`fipsmodule.cnf`) `fipsinstall` produced. Already generated in this
  checkout; rerun the setup script if you need to regenerate it (e.g. for
  a different OpenSSL version).
- `openssl-fips.cnf` — the OpenSSL config that activates the FIPS
  provider. Generated by the setup script.

## Build

```sh
cmake -S . -B build
cmake --build build -j
```

## Run

Without any special environment, the program still runs, but only ever
gets the FIPS provider if one happens to already be installed
system-wide (it usually isn't), and warns loudly when it falls back to
the non-FIPS-validated default provider:

```sh
./build/fips_file_crypt
```

To actually run in FIPS mode, point OpenSSL at the module and config
built by the setup script:

```sh
OPENSSL_MODULES=$(pwd)/fips-module \
OPENSSL_CONF=$(pwd)/openssl-fips.cnf \
  ./build/fips_file_crypt
```

You should see `FIPS provider loaded and active.` and
`Using AES-256-GCM from provider 'fips'`.

With no arguments the program runs a self-contained demo under `demo/`:
it generates a key, writes `plaintext.txt`, encrypts it to
`plaintext.txt.enc`, decrypts that back out, and checks the round trip
matches.

It also has explicit subcommands for driving it manually:

```sh
./build/fips_file_crypt genkey   demo/master.key
./build/fips_file_crypt encrypt  demo/master.key some_file.bin some_file.bin.enc
./build/fips_file_crypt decrypt  demo/master.key some_file.bin.enc some_file.bin.out
```

## Rebuilding the FIPS module

`fips-module/` is already populated, but if you need to regenerate it
(a clean machine, a newer certificate, etc.):

```sh
./scripts/setup_fips_module.sh
```

This downloads OpenSSL 3.1.2 source directly from `openssl.org` (not a
GitHub release — see below), verifies its SHA-256 against the value
published there, builds `providers/fips.so`, and runs
`openssl fipsinstall -pedantic` against it, which performs the mandated
known-answer self-tests (AES, SHA-2/3, RSA, ECDSA, the DRBGs, ...) and
records proof of that (an HMAC over the module) plus the
Approved-mode-required settings in `fips-module/fipsmodule.cnf`. Only a
module + `fipsmodule.cnf` pair produced this way will load — you cannot
just copy a `fips.so` from elsewhere, and you cannot skip `-pedantic`.

## Compliance basis — what this actually is and isn't

The module in `fips-module/` is built from the **exact source
distribution** named in the Security Policy for CMVP certificate
**#4985** — "OpenSSL FIPS Provider", OpenSSL 3.1.2, FIPS 140-3, Overall
Level 1, status **Active**, sunset **2030-03-10**. Certificate:
https://csrc.nist.gov/projects/cryptographic-module-validation-program/certificate/4985,
Security Policy:
https://www.openssl-library.org/source/fips-doc/openssl-3.1.2-security-policy-2023-12-29.pdf.

This matters because two older certificates for the same module
(**#4282** and **#4811**, covering OpenSSL 3.0.8/3.0.9 under
**FIPS 140-2**) go **Historical on 2026-09-21** — do not build new work
against those, and re-check the certificate's status before relying on
any of this, since CMVP status can change.

Cert #4985's Security Policy lists **Ubuntu Linux 22.04.1 Server**
(x86-64, gcc 11.2.0) as one of its **Tested Operational Environments**
(Table 2), and states: *"The operational environment for the Module is
modifiable as it runs in General Purpose Computers (GPC) ... no
operational environment restrictions are required for operation in the
approved mode."* That's what makes deploying this module in an
ordinary Ubuntu-based Docker image a legitimate use of the certificate
— not merely "close enough" — as long as you also satisfy the
Security Policy's other conditions:

- **Approved-mode settings must be exactly as `fipsinstall -pedantic`
  sets them** (Security Policy §2.ii): `security-checks=1`,
  `conditional-errors=1`, `drbg-no-trunc-md=1`,
  `tls1-prf-ems-check=1`. Never override these to `0`, and never patch
  or relink the built module.
- **Only algorithms in the Security Policy's Table 3 (Approved) and
  Table 4 (Non-Approved-but-Allowed) run in Approved mode.** AES-256-GCM
  (what this example uses) is Approved. Table 5 explicitly
  **disallows** Triple-DES, Ed25519, Ed448, X25519, and X448 in
  Approved mode — don't reach for those elsewhere in the codebase for
  anything that needs to be FIPS-covered.
- **Entropy**: the calling application must provide/rely on an
  SP 800-90B-compliant entropy source of ≥256-bit strength (the
  module's DRBG is seeded from the OS's entropy source by default —
  don't override that with something weaker).
- **fipsinstall must be run on every machine/image build** that will
  run the module — never copy `fipsmodule.cnf` from one build to
  another, since it's tied to that specific module file's measured
  checksum.

**One open item I'd flag to your security/compliance reviewer before
shipping:** the Security Policy (§2.ii.a, "AES-GCM Usage") describes
the module's own internal DRBG-based GCM IV generation path in detail,
and separately states that *"an IV must not be imported for encryption
from outside the cryptographic boundary of the Module"* in Approved
mode. This example generates the IV itself via `RAND_bytes()` (which
does draw from the FIPS-approved DRBG once the provider is active) and
passes it into `EVP_EncryptInit_ex2` — which is the long-standing,
ordinary pattern for GCM outside of TLS/SSH, but I can't fully rule out
that the Security Policy's "import" language is aimed specifically at
this pattern rather than at genuinely-foreign (non-DRBG-sourced) IVs.
Get this specific point confirmed against IG C.H by whoever signs off
on your FIPS compliance claim before treating file-level AES-GCM
encryption-at-rest as settled.

For a production build pipeline, pin the exact steps in
`scripts/setup_fips_module.sh` into your Docker build (verified
checksum, `-pedantic`, no cache reuse of a `fips.so` built any other
way), and re-run it as part of image builds so `fipsinstall`'s
self-tests execute on the actual build host each time.

## Key points this example demonstrates

- The FIPS provider is **never** the implicit default; it must be
  loaded explicitly (`OSSL_PROVIDER_load(NULL, "fips")`) and, in
  practice, activated via an `openssl.cnf` that `.include`s the
  `fipsmodule.cnf` `fipsinstall` produced.
- Fetch algorithms with the `"fips=yes"` property query
  (`EVP_CIPHER_fetch(NULL, "AES-256-GCM", "fips=yes")`) so a missing/
  inactive FIPS provider is a hard fetch failure, not a silent
  downgrade to a non-validated implementation.
- Whether you're "in FIPS mode" is a runtime property of the OpenSSL
  configuration in effect (`OPENSSL_CONF` / `OPENSSL_MODULES`), not
  something a binary can guarantee at compile time — this program
  checks and reports it at startup instead of assuming it.
- The demo key is generated with `RAND_bytes()`, which — once the FIPS
  provider is active — draws from its approved CTR-DRBG rather than the
  default provider's DRBG.
- AES-256-GCM is used as an AEAD: ciphertext integrity/authenticity is
  verified via the GCM tag on decrypt, and a fixed context string is
  passed as additional authenticated data (AAD) as an example of
  binding ciphertext to context without hiding it.
- The on-disk key file is purely illustrative of "here is where key
  material would go" — a real "encryption at rest" design should pull
  the key from a KMS/HSM or a wrapped-key scheme, not store it next to
  the ciphertext.
